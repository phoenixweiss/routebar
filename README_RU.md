# RouteBar

<p align="center"><strong>Выбранные адреса — в обход VPN.</strong></p>

<p align="center"><a href="README.md">English version</a></p>

RouteBar — утилита для macOS на ранней стадии разработки, которая управляет
небольшими явными группами адресов, направляемых через текущий физический шлюз,
а не через активный VPN-маршрут.

В основе проекта — человекочитаемая YAML-конфигурация, автоматический системный
процесс с правами root и нативное приложение с меню и обычным окном состояния.
RouteBar не является VPN-клиентом и не заменяет и не перенастраивает системный
маршрут по умолчанию.

## План развития

Текущая development-сборка уже умеет:

- объединять домены и необязательные фиксированные IP-адреса в именованные группы;
- разрешать каждый домен в его актуальные IPv4-адреса;
- после каждой смены сети определять физический интерфейс и шлюз заново;
- добавлять только точечные host-route и учитывать только маршруты RouteBar;
- каждые 30 секунд пересобирать маршруты после смены шлюза, DNS, пробуждения или VPN;
- отделять описание почтового транспорта от правил обхода VPN;
- показывать состояние сети, маршрутов и автоматики в нативном меню и окне macOS.

Точечные TCP-, TLS-, STARTTLS- и HTTP-проверки остаются в плане разработки.

## Конфигурация

Предлагаемый путь по умолчанию:

```text
~/.config/routebar/config.yaml
```

Это обычный YAML-файл, принадлежащий пользователю. Он может быть символической
ссылкой: исходник можно хранить в папке внешнего облачного клиента. Например,
[Yonder](https://github.com/phoenixweiss/yonder) может хранить исходник в таком
хранилище и подключать его по ожидаемому локальному пути.

Текущий формат показан в [примере конфигурации](examples/routebar.yaml).
В серии 0.x схема остаётся предварительной и может меняться между минорными
версиями.

Версия схемы 1 работает только с IPv4: при каждом построении плана все актуальные
A-записи разрешаются заново и удаляются повторы, фиксированные адреса должны быть
IPv4, а AAAA-записи намеренно игнорируются.

## Граница безопасности

RouteBar не должен ради удобства расширять исключение до подсети провайдера или
изменять default route. Перед применением изменений он заново определяет текущий
физический шлюз, повторяет DNS-разрешение и сравнивает желаемое состояние только
с ранее созданными им маршрутами.

Нативное приложение работает без повышенных прав и не меняет маршруты. Отдельный
root-owned executable предоставляет только узкие операции планирования,
применения, принятия под управление, удаления и проверки маршрутов RouteBar. Он
принимает путь к конфигурации и идентификатор профиля, но не произвольные
shell-команды. Привилегированное состояние всегда хранится по фиксированному
root-owned пути `/var/db/routebar/state.json`.

## Текущая development-сборка

Текущая сборка умеет:

- строго читать и семантически проверять версионированный YAML;
- находить физический IPv4-шлюз, игнорируя default-route VPN и bridge;
- заново разрешать IPv4-адреса и строить план точечных `/32`-маршрутов;
- безопасно пересобирать только принадлежащие RouteBar маршруты;
- один раз принимать под управление подходящие ручные маршруты;
- запускать root-owned launch daemon для сверки каждые 30 секунд;
- при удалении убирать только маршруты, всё ещё совпадающие с состоянием RouteBar;
- показывать краткий статус в меню и подробности сети, маршрутов и daemon в окне;
- отдельно показывать почтовые и другие проверки, не создающие маршрутов.

HTTPS- и почтовые endpoint-проверки уже описываются в конфигурации, но пока не
выполняются автоматически. Launch daemon также использует один явно выбранный
профиль: автоматическое переключение по SSID остаётся в плане, поскольку
системному daemon может быть недоступно имя Wi-Fi.

## Разработка

Канонический язык проекта — английский. Пользовательская документация на русском
поддерживается одновременно с ней. Пользовательские изменения фиксируются в
[журнале изменений](CHANGELOG.md).

Для development-сборки нужны:

- macOS 13 или новее;
- Swift toolchain версии 6.

Запустить проверки и посмотреть план на примере:

```bash
script/check
swift run routebar plan --config examples/routebar.yaml --profile home
```

Параметр `--profile` явно выбирает известный профиль конфигурации. Без него
автоматический выбор использует точное совпадение SSID и останавливается, если
SSID недоступен или подходит несколько профилей.

Собрать, установить и открыть нативное приложение для текущего пользователя:

```bash
script/install-app
```

Приложение устанавливается в `~/Applications/RouteBar.app` и автоматически
запускается при входе в систему в строке меню. Полное окно можно открыть командой
**Open Window** в меню либо запустить RouteBar через Spotlight или Finder.
Переключатель **Show in Dock** оставляет доступный значок в Dock, если строка меню
переполнена. Путь к конфигурации и выбранный профиль приложение читает из
установленного системного daemon, а если его нет — использует
`~/.config/routebar/config.yaml`.

Удалить только приложение и его пользовательский LaunchAgent можно командой:

```bash
script/uninstall-app
```

Системный daemon и маршруты при этом не затрагиваются.

## Автоматическая пересборка маршрутов

Перед установкой просмотреть read-only план:

```bash
swift run routebar plan --profile home
```

Установить локальную оптимизированную сборку и системный launch daemon, указав
идентификатор профиля и при необходимости абсолютный путь к конфигурации:

```bash
script/install-daemon home "$HOME/.config/routebar/config.yaml"
```

До запроса повышенных прав установщик проверяет конфигурацию и план. Затем он
принимает уже существующие маршруты только при точном совпадении с текущим
физическим шлюзом, выполняет первую сверку и запускает системное задание с
интервалом 30 секунд. Состояние хранится от root в
`/var/db/routebar/state.json`.

Удалить daemon, его состояние и только по-прежнему совпадающие с ним маршруты:

```bash
script/uninstall-daemon
```

Оба скрипта останавливаются при несовпадении существующего launch daemon или
маршрута с ожидаемыми данными владения RouteBar.

## Версии и выпуски

RouteBar следует Semantic Versioning. Канонический источник версии — файл
`VERSION`, а примечания к будущему выпуску накапливаются в секции `Unreleased`
файла `CHANGELOG.md`.

Проект использует [Bumpster](https://github.com/phoenixweiss/bumpster): `dev` —
ветка разработки, `main` — ветка выпусков. При выпуске Bumpster запускает
`script/check`, переносит накопленные записи в датированный раздел changelog,
обновляет `VERSION` и атомарно публикует обе ветки и тег `vX.Y.Z`. Создание
GitHub Release или распространение подписанного пакета остаётся отдельным явно
запускаемым шагом.
