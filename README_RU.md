RouteBar — нативная утилита для строки меню macOS, которая оставляет небольшие
явно заданные группы IPv4-адресов вне активного VPN. Она разрешает настроенные
домены и поддерживает только точечные `/32`-маршруты через текущий физический
шлюз. RouteBar не заменяет VPN-клиент и не меняет маршрут по умолчанию.

В приложении есть краткое меню, обычное окно состояния, необязательный значок в
Dock, запуск при входе, проверка YAML, выбор профиля, состояние маршрутов и явное
управление автоматической маршрутизацией.

## Скачать

Последний публичный выпуск —
[RouteBar 0.3.0](https://github.com/phoenixweiss/routebar/releases/tag/v0.3.0)
для Mac с Apple silicon под управлением macOS 13 или новее. Скачайте DMG,
откройте его и скопируйте RouteBar в «Программы». Вместе с выпуском публикуется
контрольная сумма SHA-256.

Приложение защищено ad-hoc подписью, но пока не подписано Developer ID и не
нотаризовано. При первом запуске щёлкните RouteBar с зажатой клавишей Control,
выберите **Открыть** и подтвердите запуск.

## Что умеет RouteBar

- читает строгий версионированный YAML из `~/.config/routebar/config.yaml`;
- поддерживает обычный файл или символическую ссылку, созданную, например,
  [Yonder](https://github.com/phoenixweiss/yonder);
- объединяет домены и необязательные фиксированные IPv4-адреса в именованные
  правила;
- заново разрешает каждый домен перед построением маршрутного плана;
- каждый раз определяет текущий физический интерфейс и шлюз, а не хранит их;
- показывает план и применяет только точечные `/32`-маршруты;
- каждые 30 секунд сверяет принадлежащие RouteBar маршруты после смены сети,
  DNS, пробуждения или VPN;
- сразу перечитывает изменённый YAML и показывает, применён он или отклонён;
- показывает результат последней сверки и предупреждает, пока новая редакция
  YAML ещё не подтверждена daemon;
- показывает компактную диагностику и копирует обезличенный отчёт для issue без
  доменов, сетевых адресов, SSID, путей и содержимого YAML;
- обновляет или отключает встроенный сервис, не удаляя YAML;
- удаляет только маршруты, всё ещё совпадающие с собственным root-owned
  состоянием RouteBar.

## Как включается автоматическая маршрутизация

1. Положите корректный конфиг в `~/.config/routebar/config.yaml`.
2. Откройте RouteBar, выберите профиль и проверьте read-only план маршрутов.
3. Нажмите **Enable Automatic Routing**, чтобы зарегистрировать встроенный
   сервис. На этом шаге маршруты ещё не меняются.
4. Нажмите **Apply Routes**, чтобы выполнить первую явную сверку и запустить
   30-секундный цикл.
5. После изменения YAML нажмите **Reload Config**, чтобы сразу проверить и
   применить новую редакцию.
6. Нажмите **Disable Automatic Routing…**, чтобы остановить сверку, удалить
   только принадлежащие RouteBar маршруты и отключить сервис.

RouteBar останавливается при неверном YAML, неизвестном профиле, неоднозначном
физическом шлюзе или конфликтующем чужом маршруте. Выбранный профиль и состояние
владения маршрутами хранятся в фиксированном root-owned каталоге
`/var/db/routebar`. Привилегированный сервис принимает только типизированные
операции: он не выполняет произвольные shell-команды и не принимает произвольные
пути к конфигурации.

## Конфигурация

Конфигурация остаётся обычным пользовательским файлом:

```text
~/.config/routebar/config.yaml
```

Полная схема показана в [вымышленном примере](examples/routebar.yaml). Версия
схемы 1 поддерживает два режима групп:

- `bypass-vpn` — домены и необязательные фиксированные IPv4-адреса, создающие
  `/32`-маршруты;
- `check-only` — точки проверки соединения, которые никогда не создают маршруты.

Текущий маршрутный движок работает только с IPv4. A-записи обновляются и
дедуплицируются, AAAA-записи игнорируются. HTTPS-, TCP-, TLS- и STARTTLS-проверки
уже представлены в схеме, но приложение пока их не выполняет.

Для встроенного сервиса профиль пока выбирается явно. Автоматическое переключение
по имени Wi-Fi отключено до тех пор, пока доступ к SSID и поведение в неизвестной
сети не будут проверены без ослабления безопасной модели отказа.

## Граница безопасности

RouteBar никогда не расширяет исключение до подсети и не меняет маршрут по
умолчанию. Перед каждой сверкой он заново определяет физический шлюз, повторяет
DNS-разрешение и сравнивает желаемый план только с маршрутами, ранее записанными
как собственные.

Существующий маршрут принимается под управление только при точном совпадении с
текущим физическим шлюзом. При очистке маршрут удаляется, только пока он
совпадает с root-owned состоянием RouteBar. Применение маршрутов, изменение
конфигурации, очистка, обновление и удаление выполняются последовательно;
пересекающиеся операции безопасно отклоняются.

## Разработка

Требования:

- macOS 13 или новее;
- Swift 6;
- `librsvg` для пересборки и проверки производных файлов айдентики
  (`brew install librsvg`).

Запустить полный набор проверок и посмотреть план для вымышленного примера:

```bash
script/check
swift run routebar plan --config examples/routebar.yaml --profile home
```

Собрать и установить текущее приложение для вошедшего пользователя:

```bash
script/install-app
```

Команда `script/install-app --background` заменяет и перезапускает приложение,
не открывая окно статуса поверх текущего рабочего стола.

Собрать app bundle или локальный релизный DMG без установки:

```bash
script/build-app /tmp/RouteBar.app
script/package-release
```

В исходниках сохранён прежний установщик daemon для миграции и совместимости с
выпуском 0.2.6:

```bash
script/install-daemon home "$HOME/.config/routebar/config.yaml"
script/uninstall-daemon
```

Удалить приложение и его регистрацию запуска при входе:

```bash
script/uninstall-app
```

Удаление приложения не останавливает работающий сервис маршрутизации и не
удаляет маршруты молча. Если их нужно убрать, сначала отключите автоматическую
маршрутизацию в приложении.

## Версии и выпуски

RouteBar следует Semantic Versioning. Канонический источник версии — `VERSION`,
а пользовательские изменения накапливаются в разделе `Unreleased` файла
[CHANGELOG.md](CHANGELOG.md).

[Bumpster](https://github.com/phoenixweiss/bumpster) управляет выпусками из `dev`
в `main`. При смене версии запускается `script/check`, закрывается раздел
changelog, обновляются ссылки на выпуск в обеих версиях README и файл `VERSION`,
после чего публикуется соответствующий тег. Workflow по тегу собирает и проверяет
DMG для Apple silicon и его SHA-256, берёт описание выпуска из соответствующего
раздела changelog, проверяет черновик и только после этого публикует GitHub
Release.
